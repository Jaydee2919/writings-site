Eval Authoring:
Designing Reliable Test Cases

Traditional software testing operates on a deterministic contract: given identical inputs, the system produces identical outputs. Large Language Models violate this contract at every level. To build reliable AI systems, we must treat evaluation not as a checkbox, but as an engineering discipline.

JD
J.D. Writer & Thinker

If you write software, you likely sleep well at night because of unit tests. You assert that 2 + 2 == 4, verify that a database record commits, and push to production with confidence. The contract between code and assertion is absolute.

But LLMs introduce a chaotic variable. Even with temperature=0, floating-point non-associativity in parallel GPU math, silent model upgrades by provider APIs, and shifting context constraints ensure that you will get varying outputs over time. You cannot distinguish a genuine regression from expected statistical noise without a structured approach to designing evaluation test cases.

Reliable evaluations start with Eval Authoring: building high-fidelity, comprehensive schemas that model not just the inputs and outputs, but the entire lifecycle of the agentic interaction.

✍️ The Anatomy of a Well-Formed Eval Case

A naive eval case is just a prompt and a ground-truth string. But real agentic workflows call tools, read databases, and adapt dynamically. A robust eval case requires a rich schema that isolates inputs, outlines explicit tool assertions, and defines composite grading logic.

Below is a production-grade schema showing how a complex banking agent interaction is modeled:

eval_case_schema.yaml
id: "card-dispute-resolution-001" description: "Agent resolves dispute for fraudulent transaction" tags: ["dispute", "agentic", "critical-path"] tier: "p0" # p0=blocking, p1=warning, p2=informational domain: "cards-payments" added_by: "jayanta@xyzbank.com" added_date: "2025-03-10" input: messages: - role: "user" content: "I was charged ₹12,400 at a merchant I've never visited. Please raise a dispute." context: account_id: "{{mock_account_id}}" card_status: "active" last_transaction: { amount: 12400, merchant: "ZARA MUMBAI 001", date: "2025-03-09" } expected: tool_calls_must_include: ["raise_dispute", "send_confirmation_sms"] tool_calls_must_not_include: ["close_card"] # card should NOT be blocked without user consent response_must_contain: ["dispute raised", "7–10 working days"] response_sentiment: "empathetic" grader: type: "composite" components: - { type: "tool-sequence", weight: 0.4 } - { type: "llm-judge", weight: 0.4, model: "claude-opus-4" } - { type: "keyword", weight: 0.2 }

This structure isolates three key elements of engineering rigor:

  • Negative Assertions: It is just as important to check what the model did not do. In this scenario, closing the card without consent is a severe UX failure; asserting tool_calls_must_not_include catches it.
  • Structured Context Injection: By mocking dependencies (like last_transaction) directly in the test schema, we ensure the agent operates in a sandbox with zero side effects.
  • Composite Grading: Relying solely on exact matching is too fragile, while using LLM-as-a-judge for everything is too expensive. The hybrid approach uses fast, deterministic keyword/tool filters alongside a targeted semantic judge model.

🛡️ Gold Standard: Harvesting from Reality

A common pitfall in AI teams is writing test cases purely from developer intuition. Developers are too close to the code; they instinctively write prompts that they know their system can handle, leading to an over-fitted, artificially clean suite.

The most resilient eval suites are harvested directly from production. When a customer flags a bad response, when an agent hits an error handler, or when a human supervisor corrects an AI output — that interaction is captured, sanitized of PII, and packaged as a new test case in the regression registry.

💡 Preventing Institutional Amnesia

Every P0 incident in your production system should produce a corresponding eval case. If a prompt injection sneaks through or a payment tool fails silently, write an eval case that matches that failure pattern. This ensures that once a bug is resolved, it stays resolved forever, preventing regression as teams scale.

📐 Test Case Diversity: The Four Quadrants

Just as traditional testing divides into unit, integration, and security tests, an LLM evaluation suite must maintain a healthy balance across different dimensions of coverage:

Happy Path Coverage
The Golden Paths

The standard, success-oriented customer queries. These focus on the P90 use cases—what 90% of your users do every day. These must be fast, cheap, and run on every commit to verify that core functionality remains intact.

Edge Cases & Adversarial
The Boundaries

Ambiguous queries, foreign languages, partial inputs, and prompt injection attempts. These push the boundaries of instruction-following and force the model to handle outliers safely. Usually executed during pre-merge checks.

Regression Suite
Historical Truths

A monotonically growing library of past production failures. Once a bug is fixed, its exact input is frozen into this suite. Since these represent actual user failures, they form the primary guard against regression.

Safety & Compliance
The Absolute Barriers

Scenarios testing compliance limits, refusal guidelines, and PII leakage. These are blocking P0 checks. A failure in this quadrant immediately terminates the deployment pipeline and blocks release.

📊 The Bottom Line

Evaluation is the feedback loop that dictates how fast you can build. Without a structured, diverse test registry, you are engineering in the dark.

By moving past simple text matching and designing modular, composite-graded, production-harvested test cases, you build the core telemetry needed to iterate on prompts, upgrade models, and scale your agent architecture with absolute confidence.
